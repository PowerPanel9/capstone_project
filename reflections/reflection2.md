# Reflection #2

Pod Members: **Ardelia, Zainab, Doris**

## Reflection Questions

* Name at least one successful thing this week.

 One successful thing this week was getting the payment feature working with the help of Stripe. Payments were one of the more intimidating parts of our plan since they involve real money and secure handling of transactions between clients and providers, but the implementation ended up going smoothly. By connecting to the Stripe MCP server and following Stripe's documentation, we were able to set up secure job-completion payments without having to build our own payment system from scratch. This was a big win because it validates a core part of our marketplace — clients can now actually pay providers through the platform — and it gave the whole team more confidence heading into the rest of the sprint.

* What were some challenges you and/or your group faced this week?

 One of the biggest challenges this week came from integrating everyone's work together. Because all three of us were building the roles and onboarding feature at the same time, our tasks all depended on the same few shared files — most notably `App.jsx`, `userController.js`, and `schema.prisma`. To avoid stepping on each other, we agreed ahead of time on "contracts" (the shape of the shared data, like the `role` field and what the user object returns) and assigned single owners to the risky files, so that only one person edited `App.jsx` and Zainab's schema changes merged first to unblock everyone.

 Even with that planning, we still ran into a tricky problem after pulling everyone's branches together. When a user who had signed up for only one role tried to sign up for the second role from their profile, the app threw a 500 Internal Server Error. At first this looked like a bug in the new role-switching code, but after tracing the request flow from the frontend button all the way down to the database, we found the real cause: our local databases were out of sync with the migrations we had pulled. A teammate had added a new `categories` column, but the migration hadn't been applied to our database and our Prisma Client was still generated from the old schema. Since both `register` and `updateUser` write to `categories`, every save to the user table failed. The fix was to run `prisma migrate deploy` and `prisma generate`, then restart the backend. This was a good reminder that merging code isn't just about resolving text conflicts in Git — after pulling teammate changes we also have to run the new migrations so our database matches the code, otherwise the backend breaks in ways that are easy to mistake for frontend bugs.

* Did you finish all of your tasks in your sprint plan for this week? If you did not finish all of the planned tasks, how would you prioritize the remaining tasks on your list?  (i.e over planned, did not know how to implement certain features, miscommunication from the team, had to pivot from original plans, etc.)

 We finished most of the tasks in our Sprint 2 plan. We completed the Stripe payment feature, the fixed category filter buttons on the homepage, wiring reviews to the user profile page, the edit listing feature, and deploying the site to production on Render. Our largest task this week was the roles, onboarding, and views feature, where we let a user sign up as a Client, Provider, or Both, added the provider onboarding pages, and built the client/provider view toggle. Most of this got done, but the last piece — letting a single-role user add the second role later from their profile and then see the "Switch view" button — took longer than planned because it depended on so many shared files and surfaced the database/migration sync bug described above. Since the three of us split the roles feature into interdependent parts (role selection and onboarding, routing and the toggle, and the Instagram-style experience posts), we prioritized merging the foundational schema change (the `role` field) first so nobody stayed blocked, then rebased and merged the rest on top of it. If a piece stayed unfinished, our plan was to keep the core sign-up flow working first and treat the "add a second role later" path as the follow-up, since a brand-new user picking "Both" at sign-up already gets the full experience.

* Did the resources provided to you help prepare you in planning and executing your capstone project sprint this week? Be specific, what resources did you find particularly helpful or which tasks did you need more support on?

 The resources were helpful this week, especially for the payment feature. The Stripe documentation and the Stripe MCP server made connecting payments much smoother than expected and let us implement secure job-completion transactions without building our own payment system. Our earlier planning documents also paid off: having the API contracts and data model written out ahead of time in our project plan gave us a shared reference when we were dividing the roles feature into pieces, and writing a dedicated roles-onboarding plan (with agreed-upon "contracts" and single file owners) is what let three of us work in parallel without constantly colliding. The task we needed the most support on was Git and database workflow when merging everyone's branches — specifically understanding that after pulling teammate changes we also have to run `prisma migrate deploy` and `prisma generate` so our local database and generated client match the new schema. More guidance or a checklist on that "post-pull" routine would have saved us time debugging the 500 error.

* Which features and user stories would you consider “at risk”? How will you change your plan if those items remain “at risk”?

 We would consider our AI features the most "at risk" right now — specifically AI Matching (AI 1, "matched to someone who can do garden work"), AI Sorting for providers (AI 2), AI Listing Price (AI 3), and AI Search for style matching (AI 4). These depend on the agent returning relevant, non-hallucinated results and correctly extracting listing fields, which our plan says we won't fully validate until we test at least five different query types. If they stay at risk, we'll lean on the fallbacks we already designed (letting users search or browse manually when the agent fails or returns nothing) so the core marketplace still works even if the AI is imperfect. We'd also consider the "switch to the other role after signing up for only one" flow at risk, since it touches the most shared files and is the most sensitive to database/migration sync issues across the team. To reduce that risk, we'll make running new migrations after every pull a required team habit, and keep the plain single-role sign-up and the "Both" option working as the reliable path so a shaky add-a-role-later feature never blocks a user from using the app.
